# Guardian hooks (proposed, not installed)

Two Claude Code `PreToolUse` hooks (the bash one also screens connector tools) that turn the Guardian's rules into blocks. Claude Code treats `CLAUDE.md` as context, not enforcement; hooks are the part that actually stops a call. Installing them changes shared config (class R2), so the owner approves it with a Preflight Brief. Nothing here is active until then.

> **These hooks are a guardrail, not a security boundary.** They read the text of a command and refuse the well-known mistakes, with a message that says what to do instead. They do not make a session safe against a program that is trying to get around them: it can run a script it wrote earlier, call a program the parser has never heard of, or use an encoding. A session that holds the owner's GitHub credentials can do anything the owner can. Real limits live in GitHub (branch protection, push protection) and in which credentials a session is given. Where the parser does not understand a form, it blocks rather than guessing.

| File | Job |
|---|---|
| `guard_bash.py` | Reads each Bash command (never runs it) and blocks it, or stays silent. |
| `guard_write.py` | Same for Write, Edit, MultiEdit and NotebookEdit: secret-looking content, credential files, protected paths. |
| `guard_lib.py` | Shell-aware parser (quotes, `&&`, `;`, pipes, `$( )`, backticks, heredocs), wrapper unwrapping, path checks, scanner call. |
| `policy.json` | Protected branches and paths, protected push refs (`poster-state`), where recursive deletes are allowed, where `gh` may publish a file from. Edit this, not the code. |
| `settings.example.json` | The block to merge into `.claude/settings.json`. |
| `test_hooks.py` | 820 checks (every bypass the reviews found has its own: the 25 round-2 shapes H01-H25, the round-3 classes, and the round-4 shapes with the rule name asserted). Run before and after any change. |

## What is blocked
- **Destructive:** recursive `rm` outside `/tmp`, `find -delete`, `git reset --hard`, `git clean -f`, `git checkout -- .`, `git restore <file>`, `git stash drop`, `git branch -D`, tag deletes, history rewrites, disk and permission commands, `shutdown`, `crontab`.
- **Main line:** force pushes, deleting pushes, `git push --all`, any push to `main` or `master` (including `git push origin HEAD` while on `main`, and after a `git checkout main` earlier in the same command), push targets built from variables or patterns, a bare `git push` while on `main`, merging or rebasing while on `main`, `gh pr merge` (with `-R/--repo` anywhere), `--no-verify`. **Round 4:** while the current branch is `main` or `master`, `git commit`, `cherry-pick`, `revert`, `am`, `reset <rev>` and `git pull <remote> <branch>` are blocked (`local-main-change`; a plain `git pull` is allowed), as are `git update-ref` and `git branch -f/-m/-c` on a protected branch and `git fetch <remote> x:main`. A push to `poster-state` (named, `HEAD:poster-state`, `refs/heads/poster-state`, or a bare push while on it) is blocked (`push-to-protected-ref`) because that branch holds the poster's claim records; only `poster_gate.py` changes it. `gh pr close/ready/reopen/lock/edit`, `gh issue close/reopen/delete/lock/transfer` and `gh pr review --approve/--request-changes` are blocked (a build session comments; the owner decides). `git worktree remove --force` is blocked (`worktree-force-remove`).
- **Credentials are refused by what they are given to, not by a list of readers (round 3).** Any program that is handed a credential-bearing path (`.env`, keys, `credentials.json`, `~/.ssh`, `~/.aws`, `~/.config/gh`, `/proc/*/environ`, shell history), as an argument, as `--opt=path`, `@path`, `REV:path`, a `{a,b}` or glob that matches one in the folder, a symlink that points at one, or as a `<` input, is blocked. Only programs that merely name a path (`ls`, `test`, `echo`, `rm`, `stat`, `chmod`, `git add`) are exempt for their own arguments. Inline interpreter code that mentions a credential file is blocked too. **Round 4, folders:** a recursive or archiving program pointed at a folder is blocked when the folder is the home folder (or above it) or holds a credential file. This covers `tar`, `bsdtar`, `7z`, `cpio`, `rg`, `ag`, `grep -r` and its family, `cp -r/-a`, `rsync -a/-r`, `scp -r`, `zip -r`, and `find` with an action (`-exec`, `-ok`, `-fprint`), and also a program run with no folder argument from inside such a folder (`cd ~/.ssh && tar cf x .`). The folder is listed, never read; the walk goes four levels deep and stops after 20,000 entries (see Known limits). `find` with only `-name`/`-type`/`-print` lists names and is judged by the names in its arguments.
- **Publishing a local file (round 3):** `gh ... --body-file / -F / --notes-file`, `gh api -F field=@file` and `--input` post a file's text into a public place. They are allowed only for `-` (standard input) or a file inside the repository or `/tmp` that is not a credential or protected file and that the secret scanner finds clean (the repository is public). `gh gist create`, `gh release create/upload`, `gh repo create/fork/sync` and `gh auth status --show-token` are refused.
- **Pushes go only to a remote that already exists (round 3):** `git push` to a URL, a path, or a name `git remote` does not list is blocked (`push-to-url`, `push-unknown-remote`); so are `--repo`, `--receive-pack`, `git remote add`, `remote.*` settings (`git config`, `-c`), `GIT_SSH_COMMAND`/`GIT_CONFIG_*`/`GIT_DIR` set for one command, and edits to `~/.gitconfig` or `~/.config/git/`. Brace targets (`{main,main}`) are expanded and checked.
- **Patches (round 3):** `git apply`, `git am` and `patch` write files named inside the patch. The hook reads the patch file (never runs it) and blocks when any name in it is a protected path or a credential file at any strip level (`-p0`..`-p8`, `--directory`, `-d`, `-o`). A patch it cannot read (a pipe, `-`, a file built at run time or created in the same command) is blocked. `--check`, `--stat`, `--numstat`, `--summary` and `patch --dry-run` write nothing and are allowed.
- **Process substitution (round 3):** `bash <( ... )`, `source <( ... )`, `python3 <( ... )` run text the hook cannot read and are blocked. `diff <(a) <(b)` is fine.
- **Secrets:** a `git commit` whose staged changes (or files it is about to add, or `commit -a`) contain a secret-like value or a credential file; a `git push` whose outgoing commits do; a Write/Edit whose content does; reading, printing or writing `.env`, keys and credential stores; echoing a variable named like a key. **Round 4, the environment:** `env`, `set`, bare `printenv`, `declare/typeset/readonly -p/-x` or with no arguments, and `export -p` or with no arguments are blocked (`env-dump`); `printenv NAME` is allowed only for `HOME PATH USER LOGNAME SHELL PWD LANG LC_ALL TERM TMPDIR EDITOR HOSTNAME TZ PYTHONDONTWRITEBYTECODE CLAUDE_PROJECT_DIR`; indirect expansion `${!x}` and `${!GITHUB*}`-style prefixes are blocked, as is inline `python -c`/`node -e`/`ruby -e`/`perl -e`/`awk` code that reads `os.environ`, `getenv`, `process.env`, `ENV` or `ENVIRON` (`print-secret-variable`); `git credential fill/approve/reject` is blocked (`git-credential`). **Round 4, text that becomes public:** the whole command line (commit and tag messages, `gh` comment and PR bodies, `gh api -f body=`, here-documents and here-strings, any argument) goes through the secret scanner, and a hit blocks the command without printing the value (`secret-in-command`); a message read from a file with `git commit/tag -F` or `--file` is scanned too (`secret-in-message`). The scanner is pattern based (see Known limits). The block message gives rule, file and line, never the value.
- **External and privileged:** `curl`/`wget` with a non-GET method or an upload (R4), `nc`, remote copies, download-and-run, `sudo`, `gh` commands that change settings, secrets or run the poster, every `gh api` write (any spelling: `-X PUT`, `-XPUT`, `--method=PUT`, or `-f` fields) except the three narrow ones below. **Round 4:** `ssh`, `mosh`, `telnet`, `ssh-keygen/-add/-copy-id` (`remote-shell`); `docker/podman/nerdctl/docker-compose run, exec, build, up, cp, push, login ...` (`container-run`; `ps`, `images`, `logs` are allowed); `pip/uv/npm/npx/pnpm/yarn/bun/deno` installs from a URL, a git address or an `owner/repo` shorthand, and `cargo install --git` (`install-from-url`; plain registry names are allowed); file servers and tunnels such as `python3 -m http.server`, `php -S`, `ngrok` (`serve-files`); `awk` programs that shell out (`inline-code`); `rsync --delete*` and `shred` outside `/tmp` and `/var/tmp` (`recursive-delete`, `irreversible-overwrite`).
- **Protected paths** (policy.json): `.git/`, `.github/workflows/`, `.claude/settings*.json`, `.claude/hooks/`, these hooks, `agent-system/contracts/`. **Round 4, ways to write one:** besides redirects, `cp/mv/tee/sed -i/rsync/install/ln` and patches, the hook now checks `dd of=`, `curl -o/--output/--output-dir`, `wget -O/-o/-a/-P`, `tar -x -C`, `unzip -d` (and `tar -x` run from inside a protected folder), and the editors `ed ex vi vim nvim nano emacs micro` and `sponge`. A write through an existing symlink that points into a protected folder is blocked for redirects, the programs above and the Write/Edit tools (the real path is compared). Creating such a symlink with `ln -s` was already blocked.

## How commands are read
- **Wrappers are peeled off** until the real program is found: `bash|sh|zsh|dash|ksh -c` with any option cluster (`-lc`, `-ec`, `-xc`, `--login -c`, `-o pipefail -c`), `busybox APPLET`, `env` (with `-u`, `-C`, `-S`), `timeout`, `nice`, `ionice`, `stdbuf`, `nohup`, `time`, `command`, `exec`, `setsid`, `xargs`, `find -exec`, and the shell keywords `if then else while do ! { }`.
- **Default deny.** A wrapper option the hook does not know, a program name built at run time (`$CMD`, `$'\x72m'`, `$(...)`), a wrapper that runs another command in a way it cannot follow (`watch`, `flock`, `strace`, `script`, `unshare`, and similar), or inline interpreter code that shells out (`python -c "os.system(...)"`), or script text fed to a shell or interpreter on standard input (a pipe, here-document or here-string) is blocked. The message says to write the command out directly.
- **The branch is tracked inside one command line**, so `git checkout main && git push origin HEAD` is read as a push from `main`.
- **A crash blocks.** Claude Code ignores an exit code of 1, so every unexpected error is turned into exit 2.
- **Connector tools** whose names suggest merging, deleting, dispatching a workflow, protection or secrets (`mcp__*merge*` and similar) are blocked by the same hook.

## The only GitHub writes allowed through `gh api`
Posting a comment on a pull request (`repos/O/R/issues/N/comments`, field `body`), opening a pull request (`repos/O/R/pulls`, fields `title body head base draft`) and editing a comment (`PATCH repos/O/R/issues/comments/ID`, field `body`). These exist because the build protocol ends with a pull request and a comment, and `gh` GraphQL can be blocked in some environments. Anything else through `gh api` is refused.

## Unlocking a protected path for one session (owner only)
Editing the workflow, for an approved maintenance change, is blocked by default. The owner can start that session with `GUARDIAN_UNLOCK=.github/workflows/` (comma-separated exact entries from `policy.json`). The hook reads its own environment, which a command run by the agent cannot change (tested). `.git/`, `.claude/settings*.json`, `.claude/hooks/` and these hooks can never be unlocked this way.

## What is deliberately allowed
Ordinary reading, editing, testing, committing a clean change, pushing a named branch, opening a pull request, GET requests, and edits to the poster's data (`bloor-assets/`, including `state.json`). A hook cannot know which task is approved, so it blocks the dangerous class and leaves the rest to the Preflight Brief process.

## How a block works
Exit code 2 with the reason on stderr, which Claude Code feeds back to the agent. Exit 0 with no output means "no objection", never "approved". Any unreadable input, scanner failure or policy failure also blocks (fail closed).

## Limits (read these)
- A guardrail, not a sandbox or a security boundary (see the box at the top). A script written to a file and then run (`bash build.sh`), a tool the hook does not know that runs commands, or an encoding can get past a parser that reads text. GitHub's push protection and branch protection are the second layer; read `OWNER-SETUP-CHECKLIST.md`.
- **Self-merge is only stopped here.** Sessions push to GitHub as the owner (`gh0stl0nely`, an admin), so a "0 approvals" branch rule does not stop a session merging its own pull request. These hooks stop the usual routes (`gh pr merge`, `gh api -X PUT .../merge`, a push to `main`, a connector merge tool) and nothing else does. Closing the gap properly needs a second GitHub account for sessions (QUESTIONS.md Q2).
- It only runs in Claude Code sessions that load the settings. It does not affect the GitHub Actions poster run, you at a terminal, or other tools.
- The `if` filter in a hook handler is best effort (K-sec-0007), so `settings.example.json` does not use it; the scripts inspect the command themselves.
- The scanner is heuristic (token formats and entropy); it will miss unusual secrets and may flag odd strings. A false block is cheaper than a leaked key; to proceed, remove the string or ask the owner.
- The JSON field names (`tool_name`, `tool_input.command`, `cwd`) follow Claude Code's hooks page as recorded in K-sec-0007. I could not run a live Claude Code session with the hooks installed, so the first install should be checked with one harmless blocked command (for example `git push --force` on a scratch branch) before relying on them.

## Known limits
This is the list of bypass classes the hooks do **not** close, kept so nobody reads "blocked" as "safe". It will not be complete: a parser that reads text can always be walked around by something it has not been taught. Each item is a real class, not a hypothetical.

- **A script written earlier and then run** (`bash build.sh`, `python3 tool.py`, `node x.js`, `make`, `npm run x`). The hook reads the command line, never the file. A script can read a credential, push to a URL, write a protected path or post a file. Only inline code (`python3 -c`) is looked at, and only for a keyword list.
- **Names built at run time.** A variable (`F=.env; cat "$F"`), `cat "$(printf '\056env')"`, ANSI-C quoting, an encoded name, a path assembled by `echo`. The hook expands `{a,b}` and globs against the real folder, follows existing symlinks, and refuses a program name or publish path it cannot see, but it cannot evaluate a variable. A credential path passed only through a variable is not caught.
- **Credential files with names the list does not know** (`secrets.yaml`, `prod.toml`, `token.txt`, a file in a synced folder). The name list is short; it blocks a read by name. A secret inside an ordinary-looking file is only found by the scanner, and only at commit, push, publish-a-file and Write time, not at read time.
- **Other places a secret can be printed from.** `git remote -v` and `git config --list` print remote URLs that may embed a token; `ps`, other processes' environments, a clipboard, a browser profile, a password manager's CLI other than the few listed. Connector (`mcp__*`) tools are screened by name only, never by what they send, so a connector that sends mail or writes a page can carry text out.
- **Other ways to put a file on a protected path.** The hook covers redirects, `cp`/`mv`/`tee`/`sed -i`/`rsync`/`install`/`ln`, `git rm`/`git mv`, `git apply`, `git am` and `patch`. It does not cover `tar -x` or `unzip` run from the repository root with archive members that name a protected folder (only `-C`/`-d` and a protected working folder are checked), `git cherry-pick` or `git merge` of a branch that already contains a workflow change (while on `main` they are blocked, on a build branch they are not), `git checkout -B main <rev>` and `git switch -C main` (they move the local `main`), `git stash pop`, `git read-tree`, `git update-index`, `git submodule update`, `sed` with a `w` or `e` command, a patch that creates a symlink and a second patch that writes through it, a symlink created by a script, or a patch file replaced between the check and the run. For a branch that arrives with a workflow change, the control is the pull request review and branch protection, not this hook.
- **Other ways to send commits somewhere else.** A remote the owner configured to point at a surprising address, `git bundle`, `git send-email`, `git archive --remote`, and a script that calls `git` itself. Fetching or pulling from a URL is not blocked (it reads).
- **Round 4: secrets in text are found by pattern.** The command-line and message-file scan uses the same token formats and entropy rules as the file scanner. A token that is base64- or hex-encoded, split across two arguments or two files, reversed, interleaved with NUL bytes, or written in a format the scanner does not know passes. The same scan also blocks a harmless command that quotes a real-looking token (a `grep` for a fixture, for example).
- **Round 4: the credential-folder walk is bounded and named.** It runs for the programs listed under "Credentials" above. Other programs that read a folder (`du`, `python3 script.py`, `rclone`, `duplicity`, `git archive` of a path the hook cannot see, a `make` target), a folder deeper than four levels, one with more than 20,000 entries, or a credential file whose name is not on the list are not caught. `find` without an action only lists names.
- **Round 4: environment printing is blocked by form, not by value.** `printenv NAME` is allow-listed, and the shell forms and inline interpreters above are blocked. Not covered: a script file that reads the environment (see "A script written earlier"), `compgen -v` and `${!x}` forms the pattern does not match (it prints names, not values), `strings`/`xargs -0` on a copy of `/proc/self/environ` made by a script, and a secret already pasted into a file the hook does not know is secret.
- **Round 4: programs the hook has no rule for.** Cloud and orchestration CLIs (`aws`, `gcloud`, `az`, `kubectl`, `helm`, `terraform`), other package managers (`gem`, `go install`, `brew`, `apt`, `cargo install <crate>`, `pipx run`), `npx <registry package>` (it runs that package's code), `sed` with an `e` command, `ssh`-less transfers through a tool not listed (`rclone`, `aws s3 cp`), and `git` hooks or filters already present in the repository. `rm` of a single file outside the protected paths is allowed on purpose (a recursive delete is not).
- **Round 4: a plain `git pull` on `main` is allowed** (it fast-forwards from the tracked remote). A remote the owner has pointed somewhere unexpected is the owner's setting (see "Other ways to send commits somewhere else").
- **Only Claude Code sessions that load the settings.** Not the GitHub Actions poster, not a terminal, not another agent runtime. A session started with the hooks switched off is not checked at all.
- **Wrappers it does not know.** An unknown wrapper is refused, but a new program that runs another command through a spelling the parser has no entry for may be read as the wrapper itself.
- **Heuristics cut both ways.** A harmless command can be blocked (inline code that mentions the word `credentials`, a `find -name .env`), and the credential list, the scanner and the keyword lists are not exhaustive.

**The real controls are somewhere else.** These hooks are a speed bump that catches honest mistakes and a manipulated agent's first attempt. What actually holds is:
1. **Agents never hold secrets.** A session that is never given a token cannot print, post or push one. Today a session pushes to GitHub as the owner (an admin), which is more power than a build session needs; a separate low-privilege account or a fine-grained token limited to this repository (QUESTIONS.md Q2) is the fix. Anything a session can reach, a determined program can use.
2. **The GitHub-side settings** in `OWNER-SETUP-CHECKLIST.md`: a protected `main` that needs a pull request, blocks force pushes and deletions and allows no bypass; secret scanning and push protection (currently off for this repository); Actions' workflow permissions kept read-only by default.
3. **A separate review session and the owner's own merge.** No hook replaces them.
